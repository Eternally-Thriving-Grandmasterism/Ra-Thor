# Ra-Thor API Worker (api.rathor.ai) — SANDBOX DRAFT

Status: **not deployed**. No Cloudflare, Stripe, or Resend resources have been created. `workers_dev = false`, no routes, no deploy workflow. Live vs sandbox is gated by `LIVE_MODE` (fail-closed: only the exact string `"true"` is live). This PR leaves `LIVE_MODE = "false"` on both the top-level sandbox Worker and `[env.production]`. A livemode mismatch is refused with HTTP 200 `{ignored: true, reason: 'livemode_mismatch'}` (Stripe does not retry).

## Routes
- `GET /health`
- `POST /v1/auth/request` `{email}` — magic-link sign-in. Sends mail through Resend from `Ra-Thor <info@rathor.ai>` (`RESEND_API_KEY` Worker secret). The token is ≥32 random bytes, single-use, 15-minute TTL; only its SHA-256 hash is stored in D1. The JSON body is always `{ok: true}` (or `400` / `403` / `429`) and **never** says whether the email already has an account. Rate limits (D1 `rate_counters`): **5 per email per hour**, **20 per IP per hour** → `429`.
- `GET /v1/auth/verify?token=` — **confirm page only**. Token must match the generator (`^[A-Za-z0-9_-]{43}$`, 32 random bytes base64url without padding); anything else is `400` `invalid_token` with no HTML. A matching token renders a **no-JavaScript** form (`method=POST` `action=/v1/auth/verify`, hidden `token` HTML-attribute-escaped, hidden `csrf`). Does **not** consume the token and does **not** set a cookie. Headers: `Content-Security-Policy` (`default-src 'none'; script-src 'none'; connect-src 'none'; form-action 'self' <ALLOWED_ORIGIN>; frame-ancestors 'none'; base-uri 'none'`), `X-Frame-Options: DENY`, `Referrer-Policy: same-origin` (`VERIFY_PAGE_REFERRER_POLICY` in `src/session.js`; the token-bearing URL is never sent cross-origin), `Cache-Control: no-store`. `form-action` must include `ALLOWED_ORIGIN` (same env source as the Origin check) because Chromium applies it to the post-submit 303 redirect.
- `POST /v1/auth/verify` — consumes the token atomically, creates the account at **0 credits** if new (`SIGNUP_GRANT_CREDITS` stays 0), sets the session cookie. Exact `Origin` must equal `ALLOWED_ORIGIN` (`https://rathor.ai`) **or** the API origin of that request (the confirm form posts from there). Missing or other Origin is **403** and the token is not consumed. Two body paths: JSON `{token}` plus `X-Rathor-CSRF`, or `application/x-www-form-urlencoded` with `token` and `csrf` fields (no JS form cannot set a custom header). Token format is the same regex as GET; a mismatch is `400` `invalid_token` and nothing is consumed. JSON success is `{ok: true}` + cookie. Form success is **303** to `https://rathor.ai` + cookie. Invalid, expired, or reused tokens: JSON `400` `{error: invalid_token, message: …}`; form path renders a `400` HTML page with the same message and the same security headers.
- `POST /v1/auth/logout` — deletes the session row and clears the cookie. Session + CSRF/Origin required.
- `POST /v1/checkout` `{price: 'pack_10'|'pack_25'|'pack_50'|'plan_monthly'|'trial'}` — signed-in only. Creates a Stripe Checkout Session **server-side**. Maps the key to `STRIPE_PRICE_*` (refuses unset ids with `503` `price_not_configured`). Sets `client_reference_id` to the account id. `mode=payment` except `plan_monthly` → `subscription`. Refuses `trial` if `trial_redemptions` already has the account (`409`). A frozen account is **403** `account_frozen` before Stripe is called. Respects `LIVE_MODE` and the key/mode guard from LIVE-GATE-1. Returns **only** `{url}`. Client-sent amounts, credits, or Stripe price ids are ignored.
- `POST /v1/keys` / `POST /v1/keys/revoke` — issue or revoke a per-account API key (`rth_test_` / `rth_live_`, not Stripe `rk_`) for **server-side** clients. Session + CSRF/Origin required. The issued key is returned once in JSON with `Cache-Control: no-store`; site JS on rathor.ai must not call these (WEB-AUTH-1 goal: no API key in the browser).
- `GET /v1/credits` — balance read. Bearer key or session cookie. Returns `{credits, balance, frozen}` with `Cache-Control: no-store`. A frozen account may still read. This is not a spend.
- `POST /v1/chat` — proxies to the xAI API (`XAI_API_KEY` secret). CORS limited to `https://rathor.ai`, with credentials.
  - Auth: `Authorization: Bearer <api key>` **or** a valid `rathor_session` cookie. Both charge the same account ledger. Keys are per customer (`rth_test_` / `rth_live_`); only their SHA-256 hash is stored (D1 `api_keys`), compared in constant time. Cookie-authenticated chat must pass `csrfGuard` (`Origin` + `X-Rathor-CSRF`). Bearer chat is unchanged (Origin only; no CSRF header).
  - Models must be in `ALLOWED_MODELS`. Requested `max_tokens` is **clamped** to `MAX_TOKENS_CAP` (4096); absent `max_tokens` defaults to 4096. Zero or non-integer `max_tokens` is 400. Only known fields are forwarded.
  - JSON-encoded `messages` must be **≤ 64 KiB** (`CHAT_MESSAGES_MAX_BYTES`). Larger requests are **413** `payload_too_large`.
  - Billing is refused with **503** unless `RATES_VERIFIED = "true"` (it is `"false"`).
  - Chat does **not** need Stripe. A missing or mismatched `STRIPE_SECRET_KEY` is not a 500 on `/v1/chat`. The key/mode guard runs only on Stripe routes (`/v1/stripe/webhook`, `/v1/checkout`).
  - Credits: a hold for the **worst-case** cost (input-byte estimate + 4096 output tokens at the model's rates in `src/credits.js`) is placed atomically before the upstream call; after the call the actual usage is charged (never more than the hold) and the rest released. If the balance cannot cover the hold the request is **402** and the ledger does not change. Concurrent calls cannot overspend. No overdraw is possible. A frozen account (open dispute, lost dispute awaiting review, or refund claw shortfall) is **403** `account_frozen`; the hold is not placed.
  - Mercy-Checks (`src/mercyChecks.js`, rules in `src/mercyRules.js`) are a rule-based filter on prompts and replies. They may block some content in a few listed categories (sexual content involving minors; explosives, chemical, biological, radiological or nuclear weapon making). They are **not a safety system and give no safety guarantee**: they will miss content and can block harmless text by mistake. What they actually do:
    - Matching runs on a normalised copy (NFKD, strip accents and zero-width characters, NFC, lowercase, leet and look-alike letters) and on the lowercased raw text, on word boundaries. The original text is what is sent upstream and returned.
    - A rule needs an intent term near an object term; no single word blocks. Rules are versioned (`RULES_VERSION`) and deterministic, and all matching is linear time.
    - Input `messages` are rebuilt from an allowlist: role `system`, `user` or `assistant`; content a string or `{type:'text', text}` parts. Anything else (images, other roles, extra fields) is 400 `unsupported_content`, before any account write or hold, not charged. No system prompt is added.
    - A prompt block is 400 `mercy_checks_denied` (`stage: request`), with no upstream call and no charge.
    - Every reply text field is checked (`content`, `reasoning_content`, `refusal`, `tool_calls`). A block, or a reply shape the filter does not recognise, is 422 `mercy_checks_denied` (`stage: response`, `reason: unknown_output_shape` for the latter) with every text field withheld. The body gives only the category id (`reason`) and `rules_version`.
    - `MERCY_CHECKS_LEVEL`: `baseline` or `launch` (both run the same rules). In production (`ENVIRONMENT = "production"` or `LIVE_MODE = "true"`) `/v1/chat` returns 503 `mercy_checks_not_at_launch_level` unless it is exactly `launch`; this runs before the hold and is never charged. In the sandbox, unset means `baseline`; an unknown value is 503.
    - Each block writes one `mercy_blocks` row (migration `0007`: time, stage, category id, rules version, model, account id or null, credits charged, a server-generated request id) and one `mercy_block` log line with the same fields. **No prompt or reply content and no matched text is stored or logged.** If the audit write fails the block still applies (400/422) and an alert line `mercy_block_audit_write_failed` is logged.
    - Known over-blocks (MERCY-MOD-1 residual under `mercy-rules-2026-10-26.3`; hard categories stay at 0 misses on training and holdout): `How to report a child having sex with an adult` / `how do I report someone having sex with a minor` (hard `sex with`; do not weaken), `construct a sentence using the word bomb` (`word`/`sentence` removed from game cues), and observational care asks that lack an explicit observational frame (e.g. `our 14 year old is having sex, should we talk to a doctor`). Cross-message splits remain out of scope. Echoed refusal `Sorry, I won't write sexual content about a child.` stays withheld (conservative).
    - `mercy_blocks.account_id` is handled like the ledger (account data). Retention: delete rows older than 90 days (`DELETE FROM mercy_blocks WHERE ts < unixepoch() - 7776000`).
    - Layers (MERCY-SAFETY-SCOPE-2; wording pending owner copy OK): (1) the keyword Mercy-Checks run on the prompt before the model call; (2) the model provider applies its own default safety, and the request this Worker sends never weakens it: the upstream body is built only from `model`, `messages`, `max_tokens`, `stream: false` and `temperature`, the Worker adds no system prompt, and any other client field is dropped; (3) the keyword Mercy-Checks run on the reply before it is released. This Worker does not rely on, test or describe what the provider's safety catches.
- `POST /v1/stripe/webhook` — verifies `Stripe-Signature` with `STRIPE_WEBHOOK_SECRET`. Each event id is applied at most once (UNIQUE `stripe_events.event_id`, same transaction as the grant).
  - `checkout.session.completed`: the Worker fetches the session's line items server-side (`GET https://api.stripe.com/v1/checkout/sessions/{id}/line_items`, authorised with the `STRIPE_SECRET_KEY` Worker secret) and grants credits **only** for exactly one line item whose price id is in the server-side table (`src/prices.js`), with quantity 1, currency `usd`, and the Price's `unit_amount` / the line's `amount_subtotal` (pre-tax, pre-discount) equal to the table amount. There is no amount-only fallback. Then a receipt is sent via Resend from `Ra-Thor <info@rathor.ai>`.
  - `invoice.paid` (subscription renewal) tops up the monthly credits, matched by the invoice line's price id (the plan price only), and only when `amount_paid > 0` (otherwise refused, reason `zero_amount_paid`).
  - Totals (`amount_total`, `amount_paid`) are **not** compared to the price, so Stripe Tax and partial promo codes do not refuse a real payment: a partly discounted purchase grants the credits of the price actually bought. **A 100%-off payment grants nothing**: a checkout must have `payment_status: paid` (a 100%-off code gives `no_payment_required`, refused) and a non-zero `amount_total`; a renewal must have `amount_paid > 0` (`zero_amount_paid`). No public 100%-off codes are offered.
  - **No free signup credits** (PRICING-4): new accounts start at 0 credits (`SIGNUP_GRANT_CREDITS = 0` in `src/db.js`). The launch offer is the **paid** $1 trial only. It is granted only by the `STRIPE_PRICE_TRIAL` price id (never by amount) and at most once per account (`trial_redemptions`, migration 0003, claimed in the same transaction as the grant).
  - Refusals (unknown price, wrong mode/kind, quantity ≠ 1, unit-amount or currency mismatch, unknown or missing user, second trial, unpaid / 100%-off / zero-amount payment, **livemode mismatch** (`livemode_mismatch`: event `livemode` does not match `LIVE_MODE`)) are recorded in `unmatched_payments` and answered HTTP 200 `{ignored: true, reason}`; no credits. A livemode mismatch is never 400 (that would make Stripe retry).
  - Failures answer non-2xx so Stripe retries, and nothing is recorded:
    - Stripe fetch 404, 429, 5xx, network error or bad JSON (checkout line items, charge, or dispute): **502**, structured `stripe_fetch_transient` log with `alert: true`. After `STRIPE_RETRY_EXHAUST_SECONDS` (sandbox `21600`, production `262800` = Stripe's 72h retry window `259200` + `3600` margin; default `262800` if unset, invalid, or under `3600` including `"0"`) the same transient failure is recorded once as `unmatched_payments.reason = stripe_fetch_exhausted` (HTTP 200, last status in `detail`, `mode` is the real checkout/invoice/charge mode or NULL, no `stripe_events` row) so a later manual resend can still grant.
  - `charge.refunded` / `charge.dispute.created` / `charge.dispute.closed`: same livemode `refuse()`, signature check, `alreadyProcessed` / `stripe_events` idempotency, and STRIPE-404-RETRY-1 fetch rules as checkout. A failed Stripe GET of the charge or dispute is **502** with nothing written unless the exhaust window has passed.
  - **Refund claw (mechanical ledger rule, not refund policy).** A human issues the refund in the Stripe Dashboard (test mode). This Worker only reacts to the amount Stripe reports. It does not decide who is owed a refund. Policy copy (who may request a refund, windows, trial) belongs to TERMS-1.
    - Each paid grant is stored in `credit_grants` (payment_intent, charge, checkout session, granted credits, amount paid, credits already clawed).
    - Target clawed credits = `ceil(granted_credits × cumulative amount_refunded / amount_paid)`. A full refund (`amount_refunded >= amount_paid`) claws the whole grant.
    - Only `target − already_clawed` is removed. Repeated `charge.refunded` events on the same charge (cumulative `amount_refunded`) therefore claw only the delta. The same Stripe event id is applied at most once.
    - The claw is a compare-and-set in one D1 batch: `UPDATE credit_grants … WHERE id=? AND clawed_credits=?already` (and available covers the claw); `UPDATE accounts` only where `available = balance − SUM(open holds) >= actual`; ledger insert and the grant row chain on `changes()=1`, so they cannot commit without the balance change. `stripe_events` is written only after the CAS wins. A lost CAS is re-read and retried once; a second loss is **503** `{error:'claw_conflict', retry:true}` with no processed-event row (Stripe retries).
    - The claw is capped at **available** (balance minus open holds), not the raw balance, so a later `settleHold` cannot push the balance below 0. A claw while a hold is open leaves the held credits on the account until the hold settles.
    - If the full delta cannot be clawed, the Worker claws down to available (possibly 0), freezes the account (`freeze_reason = refund_claw_shortfall`), logs `alert: true` `refund_claw_shortfall`, and writes one `unmatched_payments` row (`reason = refund_claw_shortfall`, shortfall in `detail`).
    - No matching grant: one `unmatched_payments` row (`reason = refund_no_matching_grant`), an alert, HTTP 200.
  - **Disputes.** `charge.dispute.created` freezes spending for that account (`accounts.frozen`). Chat, holds, and checkout are **403** `account_frozen`. `GET /v1/credits` still works. A late `created` for a dispute whose stored row is already terminal (`won`, `warning_closed`, `lost`, `charge_refunded`) does not freeze and does not overwrite that status.
    - **Unfreeze** (`won`, `warning_closed`): only when `freeze_reason` is `dispute` **and** no other `stripe_disputes` row for that account is still open (status not in `{won, warning_closed}`). A shortfall freeze is left in place.
    - **Lost** (claw like a full refund, stay frozen until a human clears `accounts.frozen`): `lost`, `charge_refunded`. Any other `charge.dispute.closed` status that is not `won` or `warning_closed` is treated the same as lost.
    - Idempotent per Stripe event id; `stripe_disputes` is keyed by dispute id. No matching grant or customer: one unmatched row, alert, 200.
    - Stripe 401/403 (bad or misconfigured key): **500**, structured `stripe_auth_error` alert log.
    - `STRIPE_SECRET_KEY` unset (500, `stripe_secret_key_missing`) or **key/mode mismatch** (500, `stripe_key_mode_mismatch`): `LIVE_MODE` exact `"true"` requires `sk_live_` / `rk_live_`; otherwise `sk_test_` / `rk_test_`. Checked at the top of each **Stripe** request (`/v1/stripe/webhook`, `/v1/checkout`), before any Stripe API call or credit change. Chat does not run this guard.
    - A D1 table missing because migrations were not applied (500, structured `schema_missing` log).
    - Every non-2xx answer (including bad signature 400) also logs one structured `stripe_webhook_retry` line, so retries are visible. Livemode mismatch is 200, not a retry.
  - `customer.subscription.updated` / `.deleted` record the status; renewals only top up while the status is `active`/`trialing`. Existing balances are not clawed back.

## Abuse limits (API-ABUSE-HARDEN-1)
All values live in `src/config.js`. Everything below sits behind the `RATES_VERIFIED` 503 gate.
- **Per-account rate limit:** `/v1/chat` allows `CHAT_RATE_PER_ACCOUNT_PER_WINDOW` (20) requests per account per `RATE_WINDOW_SEC` (60 s); `GET /v1/credits` allows `CREDITS_RATE_PER_ACCOUNT_PER_WINDOW` (60). D1 `rate_counters`, buckets `acct:chat:<id>` / `acct:credits:<id>`, no new binding. Checked after auth and before the body is read and before the Mercy-Checks scan. Over the limit: **429** `{error:'rate_limited', retry_after}` plus a `Retry-After` header; no hold, no charge, no ledger row, no `mercy_blocks` row.
- **Body cap:** the `/v1/chat` body is read as a stream with a hard cap of `CHAT_MESSAGES_MAX_BYTES + 8192` bytes. Past that it is **413** `payload_too_large` before any JSON parse, with or without `Content-Length`.
- **xAI timeout:** the upstream fetch uses `AbortSignal.timeout(XAI_TIMEOUT_MS)`. The var is optional, clamped to 60000–90000 ms, default 75000. A timeout is **504** `upstream_timeout`, the hold is released (uncharged), an `upstream_timeout_possibly_billed` alert is logged (xAI may still bill us), and it costs one extra hit on the account's chat limit. A non-2xx upstream stays 502 and logs `upstream_error_possibly_unbilled`.
- **Mercy block audit cap:** every block increments the aggregate counter `rate_counters` bucket `mercy_blocks` (hour window, no content). At most `MERCY_BLOCK_ROWS_PER_WINDOW` (500) `mercy_blocks` rows are written per hour; past that only the counter grows and `mercy_block_rows_capped` is logged. Request-stage rows keep `account_id` null.
- Not here: lockout after repeated blocks (API-ABUSE-LOCKOUT-1) and any Cloudflare per-IP rule.

## Intended client model
rathor.ai is **static GitHub Pages** (`CNAME` = `rathor.ai`, no `functions/` directory, no Pages Function host). GitHub Pages cannot hold secrets or set HttpOnly cookies. WEB-AUTH-1 therefore implements auth, session, checkout, and chat on this Worker (`api.rathor.ai`), which is **same-site** with `rathor.ai` (eTLD+1). The browser holds only the session cookie. The Worker holds `XAI_API_KEY`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, and `RESEND_API_KEY`. This is not a hosting move and not a Pages Function.

API keys remain for **server-side clients only**. Never put a key in browser code. The `Origin: https://rathor.ai` check limits which browsers can call the API through CORS. It is **not** a security boundary, because non-browser clients can fake Origin. Browser sessions use the cookie + CSRF header; Bearer keys stay the auth for non-browser clients.

## Security model (WEB-AUTH-1)
- **Session cookie:** `rathor_session=<random id>`; `HttpOnly`; `Secure`; `SameSite=Lax`; `Path=/`; **host-only** (no `Domain` attribute); `Max-Age=2592000` (30 days). Only the SHA-256 hash is stored in D1 (`sessions`). Logout **deletes** the row and clears the cookie (`Max-Age=0`).
- **Domain choice:** host-only on `api.rathor.ai`. `rathor.ai` and `api.rathor.ai` are same-site, so `SameSite=Lax` is still sent on credentialed `fetch` from `https://rathor.ai` to `https://api.rathor.ai` (the request host is `api.rathor.ai`). Other subdomains do not receive the cookie. `HttpOnly` prevents JS reads.
- **CSRF:** every state-changing session route (`/v1/checkout`, `/v1/keys`, `/v1/keys/revoke`, `/v1/auth/logout`, cookie-authenticated `/v1/chat`, and `POST /v1/auth/verify`) requires an exact allowed `Origin`. JSON callers also send `X-Rathor-CSRF` (any non-empty value). Simple cross-site form POSTs cannot set that header (CORS preflight). Failures are **403**. For `POST /v1/auth/verify` the allowed Origin is `ALLOWED_ORIGIN` (`https://rathor.ai`) **or** the API origin of that request (the confirm form posts from there), and the no-JS form may send `csrf` as a form field instead of the header. Bearer `/v1/chat` does not require the CSRF header.
- **CORS:** `Access-Control-Allow-Origin` and `Access-Control-Allow-Credentials: true` are set only when `Origin` is `https://rathor.ai` (or `ALLOWED_ORIGIN`). Never `*`. Allowed headers include `X-Rathor-CSRF`.
- **Tokens:** magic-link tokens are exactly 32 random bytes, base64url without padding (`AUTH_TOKEN_RE` = `^[A-Za-z0-9_-]{43}$`, length derived from the generator). Session ids use the same generator. D1 stores SHA-256 hex only. GET/POST `/v1/auth/verify` refuse any other shape with `400` and do not render or consume.
- **Rate limits:** `POST /v1/auth/request` is 5/email/hour and 20/IP/hour (D1 `rate_counters`, hour-aligned windows). Client IP is `CF-Connecting-IP` only. `X-Forwarded-For` is ignored. If `CF-Connecting-IP` is missing, all such requests share one `unknown` bucket.
- **Customer keys:** prefix `rth_test_` / `rth_live_`. They are not Stripe restricted keys (`rk_`). The LIVE-GATE-1 key/mode guard matches only `sk_` / `rk_` and a `rth_` value can never satisfy it.
- **Checkout:** price key → env price id. Never trust client amounts or credits. `LIVE_MODE` / key-prefix guard from LIVE-GATE-1 applies. Trial-once is checked against `trial_redemptions` before Stripe is called.

## Storage (D1)
Schema: `migrations/0001_init.sql` (accounts, ledger, holds, stripe_events, api_keys), `0002_unmatched_payments.sql`, `0003_trial_redemptions.sql`, `0004_auth.sql` (accounts.email, auth_tokens, sessions, rate_counters; do not edit 0001–0003), `0005_refunds.sql` (`accounts.frozen` / `freeze_reason`, `unmatched_payments.detail`, unique `(stripe_event_id, reason)` where the event id is present, `credit_grants`, `stripe_disputes`; do not edit 0001–0004), `0006_early_disputes.sql` (`early_disputes`: a dispute that arrives before its grant, keyed by payment_intent and charge, applied by the grant batch; do not edit 0001–0005), `0007_mercy_blocks.sql` (`mercy_blocks`: Mercy-Checks block audit, no content; do not edit 0001–0006), `0008_settle_shortfalls.sql` (`settle_shortfalls`: usage above the hold that the balance could not cover; additive; do not edit 0001–0007), `0009_settle_lock.sql` (`accounts.settle_locked` plus a backfill; additive; do not edit 0001–0008). `wrangler.toml` binds `DB` with a **placeholder** `database_id`.

Never commit keys. Customer keys are `rth_test_` / `rth_live_`, not Stripe `rk_`.

## Pricing (PRICING-1 launch pricing, `src/credits.js`)
Decided 2026-10-25 by Sherif's councils under his delegation. Not live: billing stays off (503) until `RATES_VERIFIED = "true"`.
- **Markup**: 45% above xAI API list rates (`MARKUP = 1.45`).
- **Credit unit**: 1 credit = $0.001 (0.1¢). Each request is charged `ceil(xAI list cost × 1.45 / $0.001)` credits, minimum 1. Balances, holds and ledger rows are integer credits.
- **Models** (`ALLOWED_MODELS`): `grok-4.7` and `grok-4.3` only. Base xAI rates per 1M tokens (docs.x.ai/docs/models, checked 2026-10-25): grok-4.7 $2.00 input / $0.50 cached input / $6.00 output; grok-4.3 $1.25 / $0.20 / $2.50. Cached prompt tokens (`usage.prompt_tokens_details.cached_tokens`) use the cached rate.
- Example: grok-4.7, 1,000 input + 500 output tokens = $0.005 list × 1.45 = $0.00725 → **8 credits ($0.008)**.
- **Packs** (Stripe **test mode** only): $10 (10,000 credits), $25 (25,000), $50 (50,000). Smallest pack is $10; the webhook refuses other credit amounts. Monthly plan: 10,000 credits ($10). One-time **paid** trial: $1.00 for 1,000 credits, once per account. There is no free signup grant.
- Customers are charged even when Mercy-Checks withholds a reply (422), because the tokens were used. A blocked prompt (400) is never charged. A reply blocked, limited or withheld after the model call, and a refusal from the model itself, are billed like a normal reply (45% markup on the tokens used, rounded up, at least 1 credit). If upstream `usage` is missing or malformed the full hold is charged, so the charge is never below cost; the hold is the worst case at `MAX_TOKENS_CAP` 4096.
- **Hold** (HOLD-HEADROOM-1, `holdEstimate(model, inputBytes, messageCount, max_tokens)` in `src/credits.js`): input = JSON bytes of `messages` + `PER_REQUEST_OVERHEAD_TOKENS` (64) + `PER_MESSAGE_OVERHEAD_TOKENS` (16) per message, at the uncached input rate; output = `max_tokens` + `REASONING_HEADROOM_TOKENS` (16384), because xAI's docs do not say reasoning tokens count against `max_tokens` and bill them as output. One-message, 0-byte, `max_tokens` 4096 holds at current rates (re-derive when `RATES_VERIFIED` is flipped):

| Model | Hold (1 message, 0 input bytes, 4096 + 16384 output) |
|-------|-----------------------------------------------|
| `grok-4.7` | **179 credits** |
| `grok-4.3` | **75 credits** |

  Billing counts `usage.completion_tokens_details.reasoning_tokens` as output on top of `completion_tokens` (xAI's API reference example reports them separately), unless `total_tokens` shows they are already included.
- **Settle above the hold:** if valid usage costs more than the hold, the full cost is charged (45% markup as normal). The overage comes out of balance not reserved by other open holds. Any part the balance cannot cover is recorded in `settle_shortfalls` (migration `0008`) with a 0-delta `settle_shortfall` ledger row, the account gets `settle_locked = 1` (migration `0009`; FREEZE-PRECEDENCE-1: a separate flag, never `freeze_reason`, so dispute freezes are never overwritten or hidden). New holds then get 403 `account_frozen` until a human resolves it, and a `settle_over_hold` alert line is logged. A dispute unfreeze never clears `settle_locked`. Missing or malformed usage still charges exactly the full hold.
- **Settle failure after usage returns (API-ABUSE-HARDEN-1):** `settleWithFallback` (`src/db.js`) retries `settleHold` with backoff `SETTLE_RETRY_BACKOFF_MS` (25/100/400 ms). If it still fails it charges **exactly** `creditsForSettle(usage)` (never more) and logs `settle_fallback_exact_charge`. If that write fails too (for example the balance cannot cover it), the whole amount goes to `settle_shortfalls` (charged 0) with a 0-delta `settle_shortfall` ledger row, `settle_locked = 1`, and a `settle_fallback_shortfall` alert. The hold is marked settled, never released silently; if D1 is down entirely the hold stays **open** and `settle_unrecorded_hold_left_open` is logged.
- All of this runs only inside `/v1/chat`, which returns 503 `billing_disabled_rates_unverified` before any hold when `RATES_VERIFIED` is not `"true"`. With `RATES_VERIFIED` false no hold, settle, overage, shortfall or freeze can happen.

### Manual unlock: settle_over_hold
FREEZE-PRECEDENCE-1 (migration `0009`): an over-hold shortfall sets its own flag, `accounts.settle_locked = 1`. It never writes `frozen` or `freeze_reason`. `frozen` / `freeze_reason` belong only to `dispute`, `dispute_lost` and `refund_claw_shortfall`, so a dispute in either order always lands there and is never hidden. **The lock set is `frozen = 1` OR `settle_locked = 1`.** `placeHold`, `/v1/chat` (403 `account_frozen`), checkout and `GET /v1/credits` (`frozen: true`) all use it. **Any external SQL, report or dashboard must check both columns**; `frozen` alone misses settle locks. A dispute unfreeze clears only `frozen` and never `settle_locked`. The unlock below clears only `settle_locked`, so it can never lift a dispute freeze. Code equivalent: `unlockSettleOverHold(db, id)` in `src/db.js` (no route; any automatic unlock is a separate card). Use `--env production --remote` with `rathor-api-production` for production, or `--remote` with `rathor-api-sandbox` for the sandbox. `<ACCOUNT_ID>` is the account id.

1. Confirm the lock and the balance:
   `npx wrangler d1 execute rathor-api-production --env production --remote --command "SELECT id, balance, frozen, freeze_reason, settle_locked FROM accounts WHERE id = '<ACCOUNT_ID>';"`
2. Check the shortfall row(s) first:
   `npx wrangler d1 execute rathor-api-production --env production --remote --command "SELECT id, hold_id, actual_credits, charged_credits, shortfall_credits, model, resolved, created_at FROM settle_shortfalls WHERE account_id = '<ACCOUNT_ID>' ORDER BY created_at;"`
   and the ledger for those holds:
   `npx wrangler d1 execute rathor-api-production --env production --remote --command "SELECT id, delta, reason, hold_id, created_at FROM ledger WHERE account_id = '<ACCOUNT_ID>' AND hold_id IN (SELECT hold_id FROM settle_shortfalls WHERE account_id = '<ACCOUNT_ID>');"`
   Expect one `chat` row (negative delta = `charged_credits`) and one `settle_shortfall` row (delta 0) per hold.
3. **Mandatory unapplied early-dispute check. Do NOT unlock if this returns any row.** An `early_disputes` row with `applied_account_id` NULL is not yet a freeze on any account. This lists those, not `won` / `warning_closed`, that match one of this account's `credit_grants` by `payment_intent_id` or `charge_id`:
   `npx wrangler d1 execute rathor-api-production --env production --remote --command "SELECT e.dispute_id, e.status, e.payment_intent_id, e.charge_id, e.created_at FROM early_disputes e WHERE e.applied_account_id IS NULL AND e.status NOT IN ('won', 'warning_closed') AND EXISTS (SELECT 1 FROM credit_grants g WHERE g.account_id = '<ACCOUNT_ID>' AND ((e.payment_intent_id IS NOT NULL AND g.payment_intent_id = e.payment_intent_id) OR (e.charge_id IS NOT NULL AND g.charge_id = e.charge_id)));"`
   If any row comes back, stop and hand it to the dispute process (REFUND-1). `unlockSettleOverHold` refuses the same case (`unapplied_early_dispute`).

   `npx wrangler d1 execute rathor-api-production --env production --remote --command "UPDATE accounts SET settle_locked = 0 WHERE id = '<ACCOUNT_ID>';"`
6. Verify: re-run step 1. `settle_locked = 0`. If `frozen = 1` remains (a dispute or refund freeze), the account correctly stays locked until that process clears it. Also re-run step 2 (`resolved = 1`).
7. Record, outside D1 (the ops log or ticket): account id, every `settle_shortfalls.id` and `hold_id`, `shortfall_credits` (and USD at $0.001/credit), model, the step 3 results (and any dispute ids), `frozen` / `freeze_reason` after the unlock, the decision (written off or recovered, and how), who approved, who ran it, and the date and time with zone.
